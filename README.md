# MonoServer

TorrServer на C# (MonoTorrent): на телевизоре Samsung (Tizen), в Linux,
Windows и Android — служба с API [TorrServer](https://github.com/YouROK/TorrServer)
MatriX на порту 8090. До 1.0.18 называлась TorrServer-Tizen (репозиторий —
`cash94/TorrServer-Tizen`, старые ссылки GitHub перенаправляет сюда).
[TorrStream](https://github.com/cash94/TorrStream-Tizen), Lampa и другие
клиенты видят её как обычный TorrServer.

Зачем своя: на **Tizen 5.5** службе телевизора нельзя запустить ни одну программу
и загрузить свою `.so` (и файлом, и из памяти — «Operation not permitted»,
«failed to map segment»), поэтому официальный TorrServer (Go) там не работает.
Управляемый код .NET — работает. На Tizen 6 и новее эта служба — альтернатива
[no-cover/torr-streaming](https://github.com/no-cover/torr-streaming): обе
занимают порт 8090, ставьте одну.

Та же служба есть и для Linux (x64, arm64) и Windows — без установки .NET, и
приложением для Android (порт 8099).

## Установка на телевизор

Файл — `MonoServer-Tizen.wgt` из [релизов](../../releases/latest). Пакет без
подписи: подписывает тот, кто ставит, своим сертификатом Samsung (он привязан к
DUID телевизора).

1. На ТВ: Apps → набрать на пульте `12345` → Developer Mode **On**, Host PC IP —
   адрес компьютера, перезагрузить телевизор.
2. **Apps2Samsung** ([Jellyfin2Samsung](https://github.com/Jellyfin2Samsung/Samsung-Jellyfin-Installer)):
   «Custom WGT» → `MonoServer-Tizen.wgt`. Программа сама войдёт в учётную
   запись Samsung, выпустит сертификат под телевизор и подпишет пакет.
3. Или **Tizen Studio**: Certificate Manager → профиль Samsung (DUID
   телевизора), `sdb connect <IP>` → `tizen install -n MonoServer-Tizen.wgt -t <устройство>`.

Служба запускается вместе с телевизором. Значок «MonoServer» — её
запуск вручную и состояние: адрес, версия, движок. В TorrStream: Настройки →
TorrServer → «Использовать TorrServer, установленный на этом устройстве» —
адрес (IP телевизора, порт 8090) подставится сам; «Об устройстве» → «TorrServer на ТВ».

Ставилась версия под именем `TorrServer-Tizen.wgt` (до 1.0.18) или
`TorrStream-TorrServer.wgt` (до 1.0.9) — новая ставится поверх: id пакета тот
же (`TorrServr1.TorrServer`), служба та же (`online.torrstream.torrserver`).

## Linux

Одной командой — служба systemd с автозапуском (спросит порт, Enter — 8090,
проверит, свободен ли; программу для x64 или arm64 скачает из релиза):

```bash
mkdir -p ~/monoserver && cd ~/monoserver && curl -fsSL https://raw.githubusercontent.com/cash94/MonoServer/main/linux/monoserver.sh -o monoserver.sh && bash monoserver.sh install
```

Обновить уже поставленную службу до последнего релиза (порт и данные прежние):

```bash
curl -fsSL https://raw.githubusercontent.com/cash94/MonoServer/main/linux/monoserver.sh -o /tmp/monoserver.sh && bash /tmp/monoserver.sh update
```

Для службы, поставленной с `--system`, — `bash /tmp/monoserver.sh update --system`.
Служба, поставленная до 1.0.18 (`torrserver-tizen`, скрипт `torrserver.sh`),
этой же командой переносится в `monoserver` — с её портом и данными; прежняя
команда с `torrserver.sh` тоже работает (он скачивает и запускает `monoserver.sh`).

Скрипт `linux/monoserver.sh` (он же в архивах релиза):

| Команда | Что делает |
|---|---|
| `./monoserver.sh install` | поставить службу и запустить; повторно — сменить порт |
| `./monoserver.sh update` | скачать последний релиз и перезапустить службу |
| `./monoserver.sh status` | состояние и адрес для TorrStream, Lampa |
| `./monoserver.sh log` | журнал службы |
| `./monoserver.sh code` | код первого входа в веб-интерфейс (пока пароль admin не задан) |
| `./monoserver.sh uninstall` | удалить службу (данные остаются) |
| `./monoserver.sh run` | запустить в терминале, без службы |

`-p ПОРТ` — без вопроса, `-d КАТАЛОГ` — данные (по умолчанию
`~/.local/share/monoserver`), `--system` — служба для всей системы через
sudo вместо пользовательской. Пользовательская служба стартует при загрузке
благодаря `loginctl enable-linger` (скрипт включает его сам).

Вручную, без скрипта:

```
tar xzf MonoServer-linux-x64.tar.gz
./MonoServer 8090 ~/ts-mono
```

Аргументы — HTTP-порт и каталог данных (база торрентов, настройки, кэш DHT и
метаданных); по умолчанию 8090 и временный каталог. Для Raspberry Pi и других
ARM — `MonoServer-linux-arm64.tar.gz` (64-битная система). Порт для пиров
случайный, он записан в `settings.json` (`PeersListenPort`) — откройте его в
брандмауэре, если нужны входящие соединения.

## Windows

`MonoServer-windows-x64.zip` (или `-arm64`) из [релизов](../../releases/latest) —
.NET ставить не нужно. Распакуйте и запустите `monoserver.cmd`: спросит порт
(Enter — 8090), проверит, свободен ли (занят — скажет кем), и запустит службу.

| Команда | Что делает |
|---|---|
| `monoserver.cmd` | запустить в окне (закрыть окно — стоп) |
| `monoserver.cmd 8091` | то же без вопроса о порте |
| `monoserver.cmd install` | автозапуск при входе в Windows (окно свёрнуто) и запуск сейчас |
| `monoserver.cmd uninstall` | убрать автозапуск |

Данные — `%LOCALAPPDATA%\monoserver` (до 1.0.18 — `torrserver-tizen`: каталог и
автозапуск прежнего имени `monoserver.cmd` переносит сам). Брандмауэр Windows при первом
запуске спросит разрешение для сети — разрешите для частных сетей, иначе
телевизор и телефон до службы не достучатся.

## Android (телефоны, приставки, телевизоры)

`MonoServer-Android-armeabi-v7a.apk` (большинство приставок и Fire TV, 32-битные
системы) или `MonoServer-Android-arm64-v8a.apk` (64-битные телефоны) из
[релизов](../../releases/latest). Служба там на порту **8099** — не мешает
оригинальному TorrServer (8090), если он тоже стоит; порт меняется в настройках.

В приложении: адрес сервера для TorrStream, Lampa и других клиентов, запуск и
остановка, **Настройки** (кэш, предзагрузка, подключения, порты, DHT, UPnP,
ограничения скорости, ретрекеры — те же, что у TorrServer), **Журнал**,
веб-интерфейс службы. Работает и с пультом.

Работа в фоне: на главном экране — «Отключить экономию батареи» и «Спец.
возможности» → включить «MonoServer — работа в фоне». Пока эта служба включена,
система не выгружает приложение, а после перезагрузки она же запускает сервер
(на приставках, где не приходит сигнал о загрузке). Экран она не читает.

Как устроено: служба та же (`service/*.cs`, сборка `service/mono` под .NET
Framework 4.7.2), запускается отдельной программой под **Mono из пакетов
Termux** — он собран под Android (bionic) для armeabi-v7a, arm64-v8a и x86_64.
.NET от Microsoft для Android-процессов есть только для arm64, в Termux .NET тоже
без 32-битного ARM. Mono в Termux собран без TLS, поэтому HTTPS службы
(ретрекеры, постеры, .torrent по ссылке, HTTP-трекеры) — через OpenSSL из того же
Termux (`service/mono/OpenSslHttpHandler.cs`, `Http.cs`), с корневыми
сертификатами Android. Сборка APK — `android/` (см. ниже).

## Как устроено

`service/` — .NET-служба `online.torrstream.torrserver`:

- `TorrEngine.cs` — [MonoTorrent](https://github.com/alanmcgovern/monotorrent)
  3.0.2 (MIT, чистый C#, сборка netstandard2.0). Торренты по magnet, хэшу или
  ссылке на `.torrent`; база — `db.json`, метаданные — кэш MonoTorrent,
  настройки — `settings.json`. Без читателей `TorrentDisconnectTimeout` секунд —
  торрент закрывается, как у TorrServer (после предзагрузки — не раньше чем через 2 минуты).
  Каждый трекер — отдельным уровнем (tier): MonoTorrent иначе спрашивает
  трекеры magnet по очереди до первого ответившего, даже если тот пиров не знает.
- `TrackerList.cs` — ретрекеры из [ngosang/trackerslist](https://github.com/ngosang/trackerslist)
  (`trackers_best_ip.txt`, по IP): обновляются при старте службы в фоне, не
  дольше 8 с; GitHub недоступен — список из прошлого раза или встроенный.
  Добавляются к каждому торренту (`RetrackersMode` 1), в базу не пишутся.
- `DhtBootstrap.cs` — запуск DHT в обход MonoTorrent 3.0.2: тот ищет первые
  узлы только через `router.bittorrent.com` (не отвечает), а кэш узлов пишет
  не в том формате, в каком читает, — DHT стоял на 0 узлов. Здесь — несколько
  bootstrap-серверов, кэш в читаемом виде, повторный поиск узлов раз в 2 минуты.
- `MemoryStorage.cs` — куски только в памяти (`CacheSize`, по умолчанию 64 МБ
  на торрент), на флеш телевизора ничего не пишется. Места не хватает —
  вытесняется давно не нужный кусок вне окна читателей, и его бит в bitfield
  MonoTorrent снимается (через внутреннее свойство — `/version` → `evict`),
  чтобы при перемотке назад кусок скачался снова.
- `ResponsiveMode` (по умолчанию включён, как у TorrServer): плеер получает
  блоки куска по мере прихода, не дожидаясь проверки хэша всего куска
  (`MemoryStorage.ReadAvailable`). Без этого при кусках по 8 МБ и 0,7 МБ/с плеер
  по 12 с не получал ни байта и обрывал запрос.
- `PublicIPv4` (как у TorrServer) и `PublicPort` — внешний адрес, когда провайдер
  не даёт белого IP и порт пробрасывается с VPS (WireGuard + nginx): «IP», «хост»
  или «IP:порт»; порт — из адреса, иначе `PublicPort`, иначе порт пиров. Идёт в
  `ReportedListenEndPoints` MonoTorrent: трекерам — `ip` и `port` в анонсе, в
  DHT — порт, пирам — `p` в рукопожатии. Меняется без перезапуска; в `/version` — `public`.
- `PositionPicker.cs` — StandardPicker MonoTorrent, но блоки куска под
  читателем — с его позиции, а начало куска — когда читатель уйдёт дальше:
  перемотка в середину 8-мегабайтного куска не ждёт скачивания мегабайт до неё.
- `PeerRotation.cs` — замена медленных пиров, как у TorrServer: MonoTorrent
  подключает с запасом сверх `ConnectionsLimit` (в его лимит идут и
  незавершённые подключения), лишних и самых медленных (медленнее четверти
  медианы) служба раз в 15 с отключает — из запаса адресов остаются лучшие.
- Предзагрузка (`TorrEngine.Preload`) — как у TorrServer: начало файла и,
  параллельно, конец (последние `max(кусок, 8 МБ)`: индекс MKV, moov MP4);
  окно начала — только до своего участка. Служебный кэш — первые и последние
  `max(кусок, 8 МБ)` файла, который смотрят: вне `CacheSize`, не вытесняются
  (`PieceStore.SetPinned`) — плеер берёт их и при перемотках.
- `ConnectionsLimit` по умолчанию 25, как у TorrServer (до 1.0.14 — 50).
- `PosterGuard.cs` — проверка постера, как `CheckImgUrl` у TorrServer: только
  http(s), служба сама скачивает начало файла и принимает лишь JPEG, PNG, GIF
  или WebP — `javascript:`, `data:`, SVG и страницы не пройдут. Проверка в
  фоне (до 5 с), до неё остаётся прежний постер; сервер не ответил — новый
  берётся, только если прежнего не было.
- `PeerPool.cs` — свой запас адресов (до 500, как у anacrolix): MonoTorrent
  3.0.2 держит не больше «лимит + 50» и забывает лишние адреса от трекеров и
  DHT. Когда его очередь пустеет, служба подкладывает ещё не опробованные;
  `total_peers` и `pending_peers` — с запасом.
- `WindowRequester.cs` — переделка StreamingPieceRequester из MonoTorrent:
  качается только окно у читателей (`ReaderReadAHead` % кэша вперёд), по
  порядку от позиции; очередь запросов у пира — сколько он тянет; куски вне
  окна (allowed fast, suggested) не берутся.
- `PeerConnector.cs` — подключение к пирам асинхронно, с таймаутом 4 с. В
  netstandard2.0-сборке MonoTorrent оно блокирующее, и на Tizen попытки к
  недоступным пирам висели по 2 минуты — новых подключений не было. Попыток
  сразу — до 48 (`MaximumHalfOpenConnections`): большинство адресов с трекеров
  недоступны, и при 16 попытках по 8 с список перебирался минутами.
- `Utp/` — uTP (BEP 29): в MonoTorrent 3.0.2 только TCP, uTP есть лишь в его
  master (net8.0, в NuGet не вышел) — перенесён сюда под C# 8 и netstandard2.0,
  поэтому работает во всех сборках (Tizen, Android, Linux, Windows). UDP-сокет
  порта пиров общий для DHT и uTP (`SharedUdpSocket.cs`, пакеты делятся по
  первому байту). Входящие — TCP и uTP; исходящие (`HybridPeerConnection`) —
  TCP и uTP сразу, но TCP главнее: uTP остаётся, только если TCP не подключился
  (в 1.0.20 первым был uTP — и скорость упала: по uTP отдающий пир сам
  уступает канал и проседает на потерях; раздача Ubuntu — 11–18 МБ/с против 23).
  При закрытии соединения пиру уходит ST_RESET (в master его нет, и libtorrent
  отбрасывал новое подключение как «duplicate peer-id»). Настройка `EnableUTP`
  (у клиентов TorrServer — `DisableUTP`) действует сразу, без перезапуска; в
  списке пиров `/cache` — поле `Transport`.
- `Holepunch.cs` — пробивка NAT (BEP 55, `ut_holepunch`): к пиру за NAT,
  до которого не достучаться, подключаемся через общего пира-посредника.
  MonoServer умеет все три роли: инициатор (не подключились к адресу из PEX с
  флагом 0x08 — просим приславшего свести нас), посредник (rendezvous → connect
  обоим) и цель (по connect сразу шлём uTP SYN, ядру — пир первым в очередь).
  Своего ut_holepunch в MonoTorrent 3.0.2 нет: расширение в рукопожатие — через
  его внутренний список, отправителя сообщения узнаём по соединению, которое
  дочитало его последним (ядро декодирует в том же потоке), источник адресов
  PEX — из своего PEX (`PeerExchange.cs`). Если оба встречных SYN прошли,
  остаётся одно соединение — с меньшим id SYN инициатора (обе стороны выбирают
  одно и то же; иначе MonoTorrent закрывал оба как дубли). Без uTP — только
  посредник. В `/cache`: `Diag.HolePunch` (счётчики) и у пира `Holepunch`.
- `PeerExchange.cs` — свой PEX (BEP 11, `ut_pex`) вместо PeerExchangeManager
  MonoTorrent 3.0.2. Тот слал PEX с нашим номером ut_pex (3), а не с номером
  получателя — у libtorrent 3 это `upload_only`, и раздающие пиры на libtorrent
  могли считать нас бесполезными; к тому же пир узнавал только о подключившихся
  после него, `dropped` не слался, у входящих уходил случайный порт соединения.
  Теперь у торрентов `AllowPeerExchange = false` (его PEX молчит, его экземпляры
  с пиров снимаем), а свой раз в минуту шлёт каждому пиру с ut_pex разницу с
  тем, что тот уже знает (первый раз — всех): адрес с портом приёма, флаги 0x01
  (шифрование), 0x02 (сид), 0x04 (uTP), 0x08 (ut_holepunch), 0x10 (доступен),
  до 50 добавленных и 50 ушедших. Входящий PEX разбираем сами: адреса — в ядро
  и в запас торрента (`PeerPool`). В `/cache`: `Diag.Pex`.
- `HttpApi.cs` — `/echo` (`MatriX.136 (TorrStream …)`), `/torrents`
  (add/get/set/rem/list/drop/wipe), `/stream?link=…&index=N&play|stat|m3u|preload`,
  `/play/<хэш>/<N>`, `/cache`, `/settings` (имена BTSets), `/download/<МБ>`;
  файлы — с Range, HEAD, keep-alive; CORS и Private Network Access. Служебное:
  `/version` (JSON; память: `rss_mb`/`peak_rss_mb` — весь процесс, `gc_mb` — куча
  .NET вместе с кэшем кусков и несобранным мусором, `memory_mb` — сам кэш,
  `threads`, `gc_count`; `?gc` — сначала полная сборка мусора и `gc_freed_mb`;
  та же сборка сама идёт через 10 с после закрытия торрента — в .NET 7+ в
  режиме Aggressive, который отдаёт память ОС: без неё массивы кэша лежали
  мусором до случайной полной сборки, на VPS процесс в простое 203 МБ против 178;
  и ещё раз через 2 минуты: закрытый TorrentManager с пирами и соединениями
  держат анонсы «stopped» на UDP-трекеры — MonoTorrent ждёт их до 45 с на
  connect и столько же на announce, и первая сборка его не застаёт. Навсегда
  же закрытые торренты держал сам MonoTorrent 3.0.2: `DiskManager.IncrementalHashes`
  хранит пошаговые хэши по ключу (TorrentManager, кусок), а недохэшированные куски
  (закрыли или перемотали посреди куска) оттуда не уходят — живая куча росла с
  каждым торрентом. При закрытии такие записи и адреса PEX удаляются (`ForgetClosed`)),
  `/log` (журнал: сводка по пирам, трекерам и DHT, кто что
  читает; `?after=N` — новые строки JSON). `/cache` — как у TorrServer, плюс
  у читателя файл, позиция, сколько скачано подряд вперёд (`Ahead`) из окна
  (`Window`), откуда пиры, с `"peers":true` — список пиров.
- `Accounts.cs` — база MonoServer `monoserver.db` ([LiteDB](https://github.com/litedb-org/LiteDB)
  5.0.21, MIT: встраиваемая, на чистом C#, с журналом и транзакциями — после сбоя
  посреди записи восстанавливается сама; SQLite и другие тянут нативный код, а на
  Tizen 5.5 и в Mono из Termux своё нативное не загрузить). Пользователи (пароль —
  PBKDF2, срок: бессрочно / до даты, блокировка, заметка, ключ для ссылок), сессии
  веб-интерфейса (30 дней), список торрентов каждого пользователя, трафик по дням
  (хранится 400 дней), доступ, узлы балансировки. Всё держится в памяти, в базу
  пишется только изменённое; трафик — раз в 15 с. Не открылась — отложена рядом
  (`monoserver.db.<дата>.bad`), служба начинает новую.
  Торренты: движок один на всех (одна раздача качается один раз), у каждого
  пользователя свой список с названием, `data` и категорией поверх неё; торрент
  уходит из движка, когда его нет ни в одном списке и никто его не смотрит.
  Торренты из `db.json` прежних версий при первом запуске — в список admin.
  У торрента — `tmdb_id` и `seasons` (`/api/info` → `features: torrent_meta`):
  `/torrents` add и set принимают `tmdb_id` (число или строка) и `seasons`
  (список или строка `"1,2,5-7"`), `/stream?save&tmdb_id=…&seasons=…` — тоже;
  в ответах list/get они полями. TorrStream пишет их при добавлении (название —
  `[TorrStream] Имя`) и берёт отсюда, а не из названия, как у TorrServer
  (`[603] Матрица [сезон 1-3]`).
- `Auth.cs` — кто спрашивает. Веб-интерфейс — только служебный `admin`: при
  первом запуске пароля нет, в журнале — «Первый вход в веб-интерфейс: код
  NNNN-NNNN»; страница входа (`web/login.html`) спрашивает код, затем новый
  пароль. Код ещё и в файле `setup-code.txt` в каталоге данных (на Linux его
  покажет `monoserver.sh code` — журнал пользовательской службы сохраняется не
  везде), на Android — в «Журнале» приложения, на Windows — в окне службы. На
  Tizen журнала не видно: код показывает страница пакета MonoServer на
  телевизоре (`GET /api/setup/code` — только сборке для Tizen и только запросу
  прямо с 127.0.0.1 со страницы пакета, origin `file://`; остальным 404).
  После пароля код больше нигде не выдаётся, файл удаляется. Потоки и API торрентов: пока в «Пользователи → Доступ» вход выключен
  (по умолчанию) — как раньше, без пароля, со списком admin; включён — Basic
  (логин и пароль, как у TorrServer с паролем: TorrStream и Lampa это умеют),
  `Authorization: Bearer <ключ>`, cookie или `?token=<ключ>` в ссылке на поток
  (плейлисты `m3u` ключ подставляют сами). «Домашняя сеть — без входа» — по
  адресу клиента (за nginx на той же машине — последний из `X-Forwarded-For`).
  Десять неверных паролей с адреса — 10 минут 429. Приложение Android меняет
  настройки службы с ключом из `local.key` (заголовок `X-MonoServer-Local`).
- `AdminApi.cs` — `/api/…`: `GET /api/info` (без входа: `name: "MonoServer"`,
  версия, нужен ли вход, кто вошёл — по нему TorrStream отличает MonoServer от
  TorrServer; ещё заголовок `X-MonoServer: <версия>` у каждого ответа),
  `POST /api/login` (→ ключ пользователя; admin — ещё cookie сессии), `/api/logout`,
  `/api/setup`, `GET /api/me`; только admin — `/api/users` (create, update: пароль,
  блокировка, срок `period` days/months/forever и `amount`, `extend`; delete, wipe,
  torrents, forget), `/api/traffic?days=N`, `/api/streams`, `/api/access`,
  `/api/master`, `/api/torrents` (remove у пользователя или у всех). Админ в
  `/torrents list` видит все торренты сервера с полем `owners`.
- `Balancer.cs` — мастер-сервер. Зритель — пользователь (без входа — адрес), у
  которого открыт поток или был открыт последнюю минуту. Здесь смотрят уже
  «Зрителей здесь, не больше» — новый зритель получает 302 на узел (другой
  MonoServer) с наименьшей долей занятых мест; кто уже смотрит здесь — остаётся,
  кого отправили на узел — туда же и дальше (10 минут); мест нет нигде — смотрит
  здесь. `/play/<хэш>/<N>` уходит на узел как `/stream?link=<magnet с трекерами>`.
  Узлу зритель приходит с подписью `?ms_user&ms_exp&ms_sig` (HMAC-SHA256 ключом
  узла, сутки): учётных записей мастера узел не знает, а Authorization браузер и
  плееры на другой адрес не переносят. Подпись открывает только `/stream` и `/play`.
  Мастер раз в 5 с спрашивает у узлов `GET /api/node/status` (`X-MonoServer-Key`):
  зрители и сколько узел отдал каждому — в трафик пользователя на мастере.
- Трафик: отдано клиентам по HTTP (всего и по пользователям), BitTorrent принято
  и отдано (по счётчикам MonoTorrent каждого торрента) — по дням, в веб-интерфейсе
  на вкладке «Трафик».
- `FileOrder.cs` — файлы и их номера как у TorrServer (`server/torr/torrent.go`):
  по пути, числа как числа (`utils.CompareStrings`), id — место в этом списке
  с 1. До 1.0.10 был порядок из .torrent, и раздачи с сериями «по размеру» так и
  показывались в клиентах; номера файлов у таких раздач с 1.0.10 другие.
- `web/index.html` (`WebPage.cs`, вшита в сборку) — веб-интерфейс на `/` (только admin,
  без входа — `web/login.html`): торренты карточками (постер, статус, скорость, пиры,
  кэш, чьи) с файлами, удобная и с телефона в вертикальном положении (вкладки внизу), карта кусков с окнами читателей (позиция, что скачано
  вперёд, что качается), пиры и трекеры, журнал вживую с фильтром, настройки,
  пользователи (создать на N дней / месяцев или бессрочно, продлить, заблокировать,
  сменить пароль, ключ для ссылок, их торренты, удалить), кто сейчас смотрит,
  трафик по дням и по пользователям, «Мастер-сервер» (узлы и ключ этого сервера как узла).
  Вкладки не уезжают за край: в узкой шапке подписи короче, в совсем узкой — одни значки.
  Открывается с телефона или ПК: `http://<IP телевизора>:8090/`. Без входа
  `/version` отвечает коротко (имя, версия — для страницы Tizen), `/log` — 401.
- `Program.cs` — обвязка Tizen, `Host.cs` — служба целиком (её же запускает `pc/`).

`app/` — страница пакета: запуск службы, состояние и адрес — IP телевизора
(`webapis.network`, иначе `lan_ips` из `/version`), а не 127.0.0.1, который работает
только на самом ТВ; кнопка «Поддержать разработчика» — QR-код с сайта. `tools/make_icon.py` — значок.

Не сделано: `/ffp` (ffprobe TorrServer), `/viewed` (отвечает пустым списком),
кэш на диске. Пиру, который просит уже вытесненный кусок, MonoTorrent отдаёт не
те данные (он не проверяет, есть ли кусок); пир отбросит их по хэшу.

## Сборка

```
python tools/build.py [--version 1.0.26] [--linux]
```

Нужен .NET SDK 8+ (Tizen.NET.Sdk и MonoTorrent скачаются сами). Результат — в
`dist/`. Проверка без телевизора: `cd service/pc && dotnet run -c Release -- 18090`.

Тег `v*` → workflow `build.yml`: версия из тега → `tools/build.py --linux` →
релиз с `MonoServer-Tizen.wgt`, `MonoServer-linux-*.tar.gz`, `MonoServer-windows-*.zip`
и `MonoServer-Android-*.apk`.

APK для Android (нужны .NET SDK 8+, JDK 11+ и Android SDK — `ANDROID_HOME` или
`android/local.properties`):

```
python android/tools/fetch-runtime.py --abi armeabi-v7a --abi arm64-v8a
cd android && ./gradlew :app:assembleRelease
```

`fetch-runtime.py` собирает `service/mono`, берёт Mono и OpenSSL из пакетов Termux
(только библиотеки, нужные по DT_NEEDED) и сборки Mono, на которые ссылается служба:
`android/app/src/main/jniLibs/<abi>` и `assets/torrserver.zip`. Для проверки в
эмуляторе — `--abi x86_64` и `assembleDebug`. В CI release-APK подписывается ключом
из секретов `KEYSTORE_B64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` (те же,
что у TorrStream-AndroidServer); без них в релиз идут debug-APK — каждый раз с
новым ключом, поверх прежней версии они не ставятся.

Сторонний код и лицензии — `service/res/THIRD-PARTY-NOTICES.txt` (MonoTorrent, MIT);
в APK для Android ещё Mono (MIT), OpenSSL (Apache 2.0), krb5 и zlib — из пакетов Termux.
